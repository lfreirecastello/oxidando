Module 01 · Ownership

Make resource lifetimes impossible to ignore.

Rust turns ownership from an implicit runtime convention into an explicit design constraint. For a polyglot engineer, the shift is less about syntax and more about making aliasing, mutation, and cleanup visible in every interface.

01 · The invariant

Ownership replaces implicit lifetime management

Rust builds resource lifetime into the type system. The same rules cover memory, files, sockets, locks, and every other value that owns cleanup work:

  1. 01Every value has an owner.
  2. 02There is one owner at a time.
  3. 03When the owner leaves scope, the value is dropped.
Polyglot bridge

Think C++ RAII with checked moves and borrows. Unlike Python reference counting or C# tracing GC, ordinary ownership and borrowing require no runtime collector.

Pythonaliasing.py
jobs = ["sync"]
alias = jobs
alias.append("report")
print(jobs)  # ["sync", "report"]
Rustownership.rs
let jobs = vec![String::from("sync")];
let mut transferred = jobs;
transferred.push(String::from("report"));
println!("{transferred:?}");
// jobs is no longer usable

Rust invalidates the source binding after the move, so two owners cannot independently destroy the same allocation. Borrow for temporary access; clone only when you need independent data.

C++raii.cpp
{
    auto resource = std::make_unique<Resource>();
} // Resource destroyed
Rustdrop.rs
{
    let file = std::fs::File::open("/etc/hosts").unwrap();
} // File dropped; handle closed

Ordinary scope exit runs cleanup. Process abort does not guarantee destructors run. Module 2 replaces the example-only unwrap() with deliberate error handling.

02 · Value semantics

Move versus Copy versus Clone

Assignment behavior depends on the type, not on whether the source happens to live on the stack. Rust separates cheap implicit duplication from explicit resource duplication.

OperationSource afterwardCost modelIntent
moveInvalidatedUsually metadataTransfer the resource
CopyStill usableCheap bitwise copyValue-like duplication
clone()Still usableType-specificExplicit duplication
Rustmove_copy_clone.rs
let retries: u32 = 3;
let saved = retries; // Copy: both remain usable

let original = String::from("Acme");
let duplicate = original.clone(); // Independent buffer
let transferred = original;      // Move: original is unusable

println!("{retries} {saved} {duplicate} {transferred}");
C++ / Python / C#

C++ std::string assignment commonly copies, while std::move leaves a valid but unspecified source. Python and C# reference assignment usually aliases. Rust String assignment does neither: it transfers ownership.

Copy permits implicit duplication. Clone is explicit, and its cost or sharing behavior depends on the type. Types requiring Drop cannot implement Copy.

03 · Mental model

Storage and ownership are separate questions

A typical local String has pointer, length, and capacity metadata. Its UTF-8 bytes occupy a heap allocation. Moving the String transfers responsibility for that buffer without cloning the bytes.

let literal: &str = "Acme";          // Borrowed static bytes
let owned = String::from("Acme");

References do not inherently imply heap storage, and stack storage does not imply Copy. Exact machine placement can also change under optimization.

04 · API contracts

Borrowing says what the callee may do

Rustcontracts.rs
fn inspect(payload: &str) -> usize {
    payload.len() // UTF-8 bytes, not character count
}

fn normalize(payload: &mut String) {
    payload.make_ascii_lowercase();
}

fn consume(payload: String) {
    println!("Sending: {payload}");
} // owned payload is dropped

let mut payload = String::from("CUSTOMER CREATED");
let bytes = inspect(&payload);
normalize(&mut payload);
consume(payload);
&TTemporary shared access

C++ const T&, plus checked lifetime and aliasing.

&mut TTemporary exclusive access

C++ T&, plus enforced exclusivity.

TOwnership transfer

For non-Copy values, similar to an owning C++ move.

C# ref exposes caller storage but does not generally prohibit other aliases. Python parameters do not express exclusivity either. For read-only text, prefer &str over &String: literals, slices, and borrowed Strings all satisfy the broader contract.

05 · The compiler's proof

Aliasing XOR mutability

While borrows overlap, safe Rust permits either multiple shared references or one exclusive mutable reference. Disjoint fields can still be borrowed separately when the compiler can prove their separation.

Rust · rejectedaliases.rs
let mut jobs = vec![String::from("sync")];
let reader = &jobs;
let writer = &mut jobs; // rejected
writer.push(String::from("report"));
println!("{reader:?}");
C++ · undefined behavior riskvector.cpp
std::vector<int> jobs{1};
const int& first = jobs[0];
jobs.reserve(jobs.capacity() + 1);
std::cout << first; // may dangle

Rust rejects mutation that could reallocate the collection while an element reference remains live. Interior mutability changes how mutation is permitted through shared references; it does not remove access rules. Module 4 covers the runtime checks and synchronization involved.

06 · Lifetime analysis

A borrow ends at its last required use

Non-lexical lifetimes let a borrow end before the enclosing scope ends. The compiler still rejects a reference that could outlive its source:

Rust · rejecteddangling.rs
fn customer_name() -> &str {
    let name = String::from("Acme");
    name.as_str() // rejected: name is destroyed on return
}
Design implication

Returning a Python or C# reference can keep an object alive. A Rust borrow does not extend its owner's lifetime. Returning the analogous C++ reference would leave it dangling.

When designing an integration API, decide whether the callee must inspect, mutate, or retain the resource. Borrow for temporary access; transfer ownership when the callee must retain it. Avoid reflexively cloning just to satisfy the compiler—first inspect the access contract and operation ordering.

Constraints

  • Print that borrowed preview; do not hardcode it.
  • Mutate and print the same customer String.
  • No clone, allocated snapshot, or unsafe.
