01 · Owned indirection

A smart pointer owns data and adds a policy

References borrow. Smart pointers usually own, act pointer-like through Deref, and clean up through Drop. Box<T> adds one-owner heap allocation.

Rustbox.rs
let config = Box::new(String::from("production"));
println!("{config}");

Use a box for recursive types, stable heap allocation, or an owned trait object. It does not create shared ownership.

Python bridge

Python objects are normally heap-managed references. Rust exposes the allocation and gives its cleanup to one statically known owner.

Java bridge

Java object allocation already produces a managed reference. A Rust Box is uniquely owned and freed deterministically when its owner leaves scope.

JavaScript bridge

JavaScript hides heap placement behind garbage-collected references. Rust uses Box where explicit owned indirection is useful.

02 · Single-thread sharing

Rc shares ownership; RefCell permits inner changes

Rc clones the owner handle, not the inner value. The allocation is dropped after the last handle disappears. Its reference count is intentionally not synchronized.

Rustlocal_shared.rs
use std::cell::RefCell;
use std::rc::Rc;

let events = Rc::new(RefCell::new(Vec::new()));
let observer = Rc::clone(&events);

events.borrow_mut().push(String::from("validated"));
println!("{:?}", observer.borrow());
Expected output["validated"]

RefCell is interior mutability: it enforces one writer or many readers at runtime. A violation panics. Rc<RefCell<T>> is only for single-threaded designs and can leak through reference cycles.

03 · Cross-thread sharing

Arc<Mutex<T>> coordinates shared mutation

Arc uses an atomic reference count. Mutex permits one lock holder at a time and returns a guard that unlocks automatically when dropped.

Rustworker.rs
use std::sync::{Arc, Mutex};
use std::thread;

let events = Arc::new(Mutex::new(Vec::new()));
let worker_events = Arc::clone(&events);

let worker = thread::spawn(move || {
    worker_events.lock().unwrap()
        .push(String::from("worker complete"));
});

worker.join().unwrap();
println!("{:?}", events.lock().unwrap());
Python bridge

This resembles shared objects protected by threading.Lock. The GIL does not replace locks for multi-step application invariants or non-Python resources.

Java bridge

This resembles a shared reference plus synchronized or Lock. Rust additionally checks whether the captured values may cross thread boundaries.

JavaScript bridge

Ordinary objects stay inside one event-loop agent. Workers usually communicate by messages; shared memory requires explicit SharedArrayBuffer and atomics.

Keep lock scopes short and use a consistent lock order. A mutex prevents data races, but not deadlocks, starvation, or incorrect business rules.

04 · Thread-safety contracts

Send and Sync let the compiler reject unsafe sharing

Send means ownership may cross a thread boundary. Sync means shared references may safely be used across threads. Most composed types receive these marker traits automatically when their fields qualify.

Rc<T>Not Send or Sync

Its count is unsynchronized.

Arc<T>Atomic shared owner

The inner type must also qualify.

Mutex<T>Synchronized interior mutation

Access is mediated by a lock guard.

Intermediate depth · recovery

A mutex becomes poisoned when a thread panics while holding it. Decide at the application boundary whether to stop, recover the inner value, or rebuild state.

Advanced depth · architecture

Prefer ownership transfer or message passing when the data naturally moves. Use shared state when multiple workers genuinely coordinate around one resource; compiler safety does not guarantee maintainable contention patterns.

Constraints

  • Keep one shared log and its mutex.
